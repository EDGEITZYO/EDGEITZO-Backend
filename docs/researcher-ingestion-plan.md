브랜치 `feat/researcher-ingest` / 2026-08-22

## 1. 이전 판정에서 바뀐 것

적재를 준비하며 API·DB를 직접 확인한 결과 4가지가 정정됐습니다.

### (1) ScienceON은 살아 있지만, 연구자↔논문 색인이 불완전하다

토큰 재발급 후 `target=RESEARCHER`가 정상 동작합니다. 그리고 기대 이상을 줍니다 —
동명이인을 **이미 분리**해 두었고(인만진 → CN 376133 / 54910), 이메일·소속·대표키워드·
논문 CN 전체 목록이 한 번에 나옵니다.

```
CN=54910 인만진 청운대학교 manjin@chungwoon.ac.kr 논문101 특허9
  API-001-01 논문 검색API → CN 101건
```

그런데 실측 매칭률이 낮습니다. 코퍼스 논문 20편의 저자 67명을 돌린 결과:

| 방식 | 매칭 | 저자당 호출 |
|---|---|---|
| 이름 검색 + 논문 CN 교집합 (기존 `ingest_researchers.py` 방식) | 15% | 3.5회 |
| 이름 + **소속** 일치로 후보 선별 후 교집합 | **46%** | **1.5회** |

못 맞추는 이유는 두 가지입니다. `TI` 검색이 정확일치가 아니라 퍼지라서
'노정해'를 치면 곽노정·노정건·노정권이 먼저 나오고(정답은 29번째), 더 근본적으로는
ScienceON이 연구자에 붙여 둔 논문 목록 자체가 빠진 게 많습니다 — '박성현' 동명이인
63명을 전수 조회해도 우리 논문(JAKO202216466710649)을 가진 사람이 없었습니다.

**결론**: ScienceON을 인물 식별의 기준으로 삼을 수 없습니다. **이메일 오버레이 전용**으로 씁니다.

### (2) 이메일은 "불가"가 아니다 — 다만 신뢰도 등급이 필요하다

매칭된 연구자의 이메일 보유율은 높습니다(기존 적재분 143/189 = 76%, 표본에서도 유사).
다만 위 46% 중 절반은 "이름+소속은 맞지만 논문 CN 교집합으로 확인은 못 한" 추정입니다.
남의 이메일을 프로필에 띄우는 값이라 근거를 구분해 저장합니다:

- `confirmed` — 이름+소속 일치 **그리고** 그 연구자의 논문이 우리 논문과 겹침
- `inferred` — 이름+소속이 맞는 후보가 **유일** (교집합 미확인)
- 후보가 여럿인데 확인이 안 되면 이메일을 **저장하지 않습니다**

화면에 어느 등급까지 노출할지는 API 계층에서 정합니다.

### (3) KCI가 나머지 11개 기능을 전부 커버한다

`articleDetail`이 저자별 구조화 정보를 줍니다:

```xml
<author author-division="1" author-part="제1">
  <name>한화정</name><name-eng>Hwa-Jung Han</name-eng>
  <institution>국립공주대학교</institution>
</author>
```

소속(기관+학과), **역할(제1/교신/참여/단독)**, **영문명**을 한 번에 얻습니다. 역할은 명세서의
"공저자를 역할과 함께"에 그대로 대응하고, 영문명은 코퍼스의 로마자 저자명 240개
(영문 학회지 JAKO)를 한글 인물에 접합하는 열쇠입니다.

### (4) 소속을 쓰면 전량 배치가 온디맨드보다 싸다

이름만으로 `articleSearch`를 치면 흔한 이름이 폭발합니다(표본 40명 중앙값 87건, 김민정 3,718건).
(3)에서 얻은 소속을 `affiliation`에 같이 넣으면 서버가 걸러 줍니다:

| 저자 | 이름만 | +소속 |
|---|---|---|
| 김선영 (광주여자대) | 2,153 | **47** |
| 김윤정 (광주여자대) | 1,439 | **53** |
| 이영미 (상명대) | 988 | **23** |
| 심규철 (국립공주대) | 210 | **13** |

페이지 수 76 → 15 (5배 감소). 온디맨드로 미룰 이유가 없어 전량 선적재합니다.

## 3. 스키마 (alembic 026~029) — 적용 완료

### 식별자 재키잉

`researchers`의 PK를 ScienceON CN에서 출처 접두어가 붙은 `researcher_id`로 교체했습니다.
기존 189행·292링크는 `sci:<cn>`으로 그대로 살아 있습니다(데이터 손실 0).

```
kci:<sha1(정규화이름|기관루트)[:16]>   KCI 파생 (기본)
oa:<openalex author id>              OpenAlex
sci:<scienceon cn>                   ScienceON에서만 확인된 연구자
```

`cn` 컬럼은 `scienceon_cn`으로 격하돼 이메일 오버레이 조인에 쓰입니다.

  `corpus_paper_count` / `first_pubyear` / `last_pubyear` / `papers_truncated` / `expanded_at`
- `researcher_papers`: `author_order` / `role` / `institution_at_time`
- `researcher_external_papers` (신규): 코퍼스 밖 논문. 저자 85%가 코퍼스에는 논문 1편뿐이라
  「총 논문 수」「연도별 이력」「연구 흐름」은 이 테이블 없이 성립하지 않습니다.

`scripts/load_researchers.py` (KCI 백본) + `scripts/load_researchers_openalex.py` (해외지)

모든 단계가 `data/checkpoints/researcher_*.json`에 중간 저장돼 중단 후 재개됩니다.

### 구현하며 실측으로 잡은 함정

1. `articleDetail`의 `<reference>` 안에도 빈 `<author>` 태그가 수십 개 있어,
   `articleInfo/author-group`으로 스코프를 좁히지 않으면 빈 저자가 딸려옵니다.
2. 기관 접미사를 짧은 것부터 매칭하면 `청운대학교`가 `청`으로 잘립니다 → 최장일치.
3. **ScienceON은 토큰당 동시 요청을 거부합니다** — concurrency 2로 30건 돌리면 10건이 실패하고,
   순차로는 8/8 전부 성공(0.1~0.3초)합니다. → ScienceON은 순차 호출 고정.
4. 두 API 모두 지속 호출 시 429를 던집니다 → 지수 백오프.
5. 한 논문에 같은 인물이 두 줄로 실리는 경우가 있어(소속을 나눠 적은 경우) `ON CONFLICT`가
   같은 행을 두 번 건드려 실패합니다 → 삽입 전 (연구자, 논문) 중복 제거.
6. `papers.id`가 혼합 포맷(JAKO 616 / NART 181 / DIKO 150 / ART 50)이라 ScienceON 논문 목록과
   교집합을 낼 때 `scienceon_cn`까지 합쳐야 합니다.

## 5. 남아 있던 설계 판단 2개 — 확정

### 총 피인용 수 → **KCI 기준으로 통일**

`articleSearch`의 `<citation-count kci="35" wos="0">`에서 **kci 속성만** 씁니다(본문 값은 kci+wos 혼합).
집계 범위가 하나라 "총 피인용 456"의 의미가 명확하고("국내 KCI 등재지 인용"), 확장 조회에
인라인으로 딸려 와 추가 비용이 0입니다. OpenAlex 피인용은 KCI에 아예 없는 해외지 저자에게만
쓰고 `citation_source` 컬럼으로 구분해, 화면에서 "KCI 피인용" / "국제 피인용"으로 라벨을
달리 붙입니다. **max() 혼합은 폐기**합니다.

### 노드 크기 → **sqrt 정규화 + 하한/상한 고정**

```
r = r_min + (r_max - r_min) * sqrt(c / c_max_in_view)
r_min = 8px, r_max = 28px, c_max_in_view = 현재 결과 집합의 최대 피인용
```

결과 집합 안에서 상대화하므로 분야별 인용 규모가 달라도 그래프가 항상 읽힙니다. sqrt는 면적
비례 인식과 맞아 log보다 중간 구간 구분이 낫습니다. `c_max_in_view == 0`인 키워드는
전원 `r_min` 균일 — 이미 명세서에 있는 폴백입니다.

**출처별로 따로 정규화해야 합니다.** KCI 중앙값 20 vs OpenAlex 709로 35배 차이라, 한 척도에
올리면 해외지에 낸 사람이 연구 영향력과 무관하게 커집니다(실측: 인만진 KCI 691이
Young‐Je Cho OpenAlex 1,952에 밀려 19.9px → 출처 분리 후 둘 다 28.0px).

**단, 계산은 프런트가 합니다**(§14). 백엔드는 `citations`와 `citation_source`만 내려줍니다.

**대안: fwci** — §12에서 수집한 분야보정 피인용(32,882편, 중앙값 1.07)을 쓰면 분야·연차가
달라도 하나의 척도로 비교됩니다. 다만 OpenAlex 쪽에는 이 값이 없어 완전 통일은 아직 안 됩니다.

## 7. 추가 적재 (2026-08-22 후속)

`expand` 단계가 `articleSearch` 응답의 저자를 파싱해놓고 저장하지 않은 누락이 있었습니다.
그 결과 「함께 연구한 사람들」이 코퍼스 논문(전체의 10%)만 반영하고 있었습니다.

| 지표 | 수정 전 | 수정 후 |
|---|---|---|
| 김수완(전남대 의대) 공저자 | 5명 | **243명** |
| 이상우 공저자 | 1명 | 130명 |
| 손홍규 공저자 | 7명 | 113명 |

`alembic 027`로 `researcher_external_papers.authors` / `author_institutions`를 추가하고
`expand`를 재수집했습니다. 공저 관계가 8,302건에서 12만 건 수준으로 늘어나,
「함께 연구한 사람들」이 온전해지는 동시에 연구자 임베딩·GNN이 쓸 만한 그래프 밀도를 갖춥니다.

### `keywords` 단계 신설

「연구 흐름 시각화」에 필요한 논문 키워드를 채웁니다. `articleSearch`는 키워드를 주지 않고
`articleDetail`만 줍니다. 같은 논문이 여러 연구자에게 중복 저장돼 있어(31,599행 / **고유 25,286편**)
논문 단위로 한 번만 호출합니다.

측정된 `articleDetail` 처리량:

| 동시성 | 건당 |
|---|---|
| 1 | 0.116초 |
| 4 | 0.075초 |
| 8 | 0.027초 (429 위험) |

동시성 4 기준 25,285편에 **약 40분**, 저장 용량은 **약 5MB**입니다.
실적재 결과 **키워드 보유 24,435편 / 없음 850편 / 실패 0편 = 96.6%** 입니다
(초기 표본에서 47%로 나온 건 `external_id` 오름차순이라 옛날 논문만 봤기 때문이었습니다). 처음에 제안했던
조회 시점 지연 채움은 폐기합니다 — 용량이 사실상 공짜인데 첫 방문자를 1초 가까이
기다리게 할 이유가 없습니다. 전량 선적재하고 런타임 대기를 0으로 둡니다.
(다만 그래프에 노드 90개를 뿌리면 읽을 수 없으므로 **표시**는 최신 20 + 피인용 상위 10으로 제한합니다.)

### 부수적으로 고친 데이터 버그

KCI 키워드가 한 태그에 여러 개 묶여 올 때의 구분자가 **U+0387(GREEK ANO TELEIA)** 인 논문이
있었습니다. 파서는 **U+00B7(MIDDLE DOT)** 로 자르고 있었고, 두 글자는 화면상 구별되지 않습니다.
그래서 `"Alcalase-enzymatic hydrolysate · Alkali treatment · Antioxidant activity"`가
키워드 하나로 저장돼 있었습니다. 중점 계열 5종을 모두 구분자로 인식하도록 고치고
기존 데이터 7명분을 정정했습니다.

**옛 KCI 레코드의 오염된 키워드** — 2000년대 초 논문에는 초록 본문이 통째로 `<keyword>`에
들어간 것이 있습니다(실측 400자). 컬럼 길이(200)를 넘겨 배치가 죽었습니다. 파서에
`clean_keyword()`를 넣어 60자 초과(코퍼스 실측 평균 13자), 한글·영숫자가 없는 값(`....`),
문장 종결어미(`하였다`·`있다` 등)를 걸러내고, 적재 시에도 200자로 한 번 더 자릅니다.
정제 후 키워드 길이 분포는 20자 이하 183,802 / 21-40자 36,720 / 41-60자 1,853(0.8%)입니다.

## 10. 연구자 임베딩 + GNN (2026-08-22)

### 왜 했나 — 명세서 방식이 실제로 안 돌아간다

명세서 「노드 그래프 뷰」는 노드 간 거리를 **"키워드 공유"** 로 재라고 합니다.
'항산화'로 분야 검색한 결과(14명, 91쌍)에서 실제로 세어봤습니다.

| 키워드 공유 | 쌍 | 비율 |
|---|---|---|
| **0개 → 거리 무한대** | **41쌍** | **45.1%** |
| 1개 | 24쌍 | 26.4% |
| 2개 이상 | 26쌍 | 28.6% |

쌍의 45%가 "완전히 무관"으로 그려집니다. 같은 분야로 검색해 나온 사람들인데도 그렇습니다.

전형적인 실패 사례입니다.

```
인만진  폴리페놀, 효소 분해, 요구르트
조민영  Alcalase-enzymatic hydrolysate, 알카리 처리, 항산화

둘 다 식품 원료를 효소로 분해해 항산화 물질을 얻는 연구인데 키워드 공유 = 0
```

### 1단계 — 내용 임베딩 (`scripts/embed_researchers.py`)

이미 프로젝트에 있는 `dragonkue/BGE-m3-ko`로 연구자의 키워드를 벡터화합니다
(대표 키워드 15개 + 논문 키워드 빈도 상위 25개). 소속·이름은 넣지 않습니다 —
재려는 건 "연구 분야가 비슷한가"이지 "같은 학교인가"가 아니라서, 소속을 넣으면
같은 대학 사람들이 전부 뭉칩니다.

**결과**: 2,752명 / 1024차원 / 134초(MPS). Postgres `researchers.embedding` + ChromaDB `researchers` 컬렉션.

**타당성 검증** — 임베딩이 키워드 공유와 같은 방향으로 움직이는지 확인:

| 그룹 | 임베딩 유사도 평균 |
|---|---|
| 키워드 공유 0인 쌍 | 0.562 |
| 키워드 공유 2개 이상인 쌍 | **0.768** |

차이 +0.206. 방향이 일치하므로 엉뚱한 값이 아니고, 그러면서 공유 0인 41쌍에도 실제 거리를 줍니다.

### 2단계 — GNN (`app/services/graphsage.py`, `scripts/build_researcher_graph.py`)

내용 임베딩은 "무슨 단어를 쓰나"만 봅니다. "누구와 함께 연구하나"는 공저 네트워크에 있습니다.

**비지도 GraphSAGE** (Hamilton et al. 2017)를 씁니다. 목적함수가
"이웃인 노드는 가깝게, 무작위로 뽑은 남남은 멀게"라 **정답 라벨이 필요 없습니다.**

```
L = -log σ(z_u · z_v) - Q · E_{n~Pn} log σ(-z_u · z_n)
```

**Neo4j GDS 대신 PyTorch로 직접 구현한 이유**: Aura에 GDS가 활성화돼 있지만(프로시저 443개)
계산에는 별도 유료 세션(`gds.session.getOrCreate`)이 필요합니다. 비용 없이 재현 가능하도록
직접 구현했습니다. Neo4j에 적재한 그래프(`:ResearcherNode`, `:COAUTHORED`)는 조회·시각화용으로 둡니다.

**그래프 규모** — §7의 외부 논문 공저 적재가 선행 조건이었습니다.

| | 코퍼스만 | 외부 논문 포함 |
|---|---|---|
| 고유 엣지 | 4,151 | **7,943** |
| 연결요소 | 496개 | 367개 |
| **최대 요소** | **59명** | **453명** |
| 10명 이상 요소에 속한 비율 | 33% | **52%** |

최대 덩어리가 59명일 때는 GNN이 배울 이웃이 없었습니다.

**학습**: 입력 = 내용 임베딩 PCA 128차원, 출력 128차원, 30 epoch, 205초(MPS).
loss 4.49 → 3.76.

### 검증 — held-out 링크 예측

학습에 쓴 엣지로 재면 외운 걸 되묻는 셈이라 과대평가됩니다(AUC 0.997).
**엣지 10%를 빼고 학습해 못 본 관계를 맞히는지** 봤습니다.

| 임베딩 | held-out AUC |
|---|---|
| 내용 (PCA 128) | 0.933 |
| **그래프 (GraphSAGE)** | **0.992** |

일반화된 결과입니다.

### 두 임베딩은 서로 다른 것을 본다

유사도 상관계수 **0.227** — 겹치는 정보가 적습니다.

| 관계 | 예 |
|---|---|
| 그래프는 가깝고 내용은 멂 | 같은 연구 그룹, 다른 주제 (그래프 0.98 / 내용 0.47) |
| 내용은 가깝고 그래프는 멂 | 같은 주제인데 협업 없음 → **공동연구 추천 후보** (내용 0.90 / 그래프 -0.44) |

### 적용 (`app/services/researcher_similarity.py`)

- **노드 간 거리** = `1 - (0.7 × 내용유사도 + 0.3 × 그래프유사도)`
  명세서가 요구하는 건 "연구 분야 유사도"라 내용에 무게를 둡니다. 그래프 임베딩만 쓰면
  공저자 유사도가 1.0에 붙어 분야가 아니라 소속 그룹으로 뭉친 그래프가 됩니다.
- **엣지 임계값 0.5** — 전부 이으면 40명일 때 780개 선이라 화면이 까맣게 됩니다.
- **노드 크기** = `8 + 20 × sqrt(피인용 / 결과집합 최대)` — **출처별로 따로 정규화**합니다.
  KCI 중앙값 19 vs OpenAlex 709로 37배 차이라, 한 척도에 올리면 해외지에 낸 사람이
  연구 영향력과 무관하게 무조건 커집니다(실측: 인만진 KCI 691이 Young‐Je Cho OpenAlex 1,952에
  밀려 19.9px, 출처 분리 후 둘 다 28.0px).
- **유사 연구자 추천** — 명세서엔 없지만 벡터가 있으면 공짜로 나옵니다.
  인만진 → 김동청(0.934) · 이태정(0.849) · 채희정(0.771). 실제 연구 그룹과 일치합니다.

### 알려진 한계

논문을 딱 한 편만 함께 쓴 연구자들은 키워드 집합이 완전히 같아 **임베딩이 동일**해집니다
(김희정·장유민·조민영 유사도 1.000). 데이터상 이들을 구분할 정보가 없으므로 값 자체는
맞지만, 노드 그래프에서 겹쳐 그려집니다. 프런트에서 충돌 회피 배치가 필요합니다.

## 11. 학위논문·미연결 논문 저자 적재 (2026-08-23)

### 발견 — 코퍼스의 17.7%가 빠져 있었다

계획서 §2에 "DIKO(학위논문) 저자 139명 — best-effort"라고 적어놓고 **실행에서 통째로 빠뜨렸습니다.**
감사하기 전까지 몰랐습니다. 원인은 적재 경로의 조건입니다.

```
anchor    → WHERE kci_art_id IS NOT NULL                    → 628편 (JAKO만)
OpenAlex  → WHERE doi IS NOT NULL AND kci_art_id IS NULL     → 219편
```

DIKO는 `kci_art_id`도 DOI도 없어 두 경로 어디에도 안 걸렸습니다. 결과적으로 논문 177편의
저자가 없었고, **저자 203명이 연구자 검색에서 아예 안 나왔습니다.**

### 세 가지 방법을 시험했고 하나만 됐다

| 시도 | 무엇 | 결과 |
|---|---|---|
| KCI 논문 검색 | 그 사람의 다른 논문 찾기 | ❌ 전부 동명이인 |
| ScienceON 연구자 검색 | 연구자 레코드 찾기 | ❌ 6명 중 1명 |
| **ScienceON 논문 조회** | **학위논문에 적힌 저자·소속 읽기** | ✅ **177/177** |

KCI가 안 되는 이유는 명확합니다 — 대학원생이라 학술지 논문이 아직 없습니다.

```
권태광(중부대) 이름 검색 13건 → 안동대·메리놀병원·연세대  전부 다른 사람
한유림(한양대) 4건, 류병석(연세대) 3건도 같음
```

이름만으로 긁었으면 **동명이인 13명이 한 사람으로 뭉쳤을 것**입니다.

성공한 세 번째는 **"찾은" 게 아니라 "읽은" 것**입니다. 이미 갖고 있던 `scienceon_cn`으로
논문 상세를 조회해 거기 인쇄된 저자·소속을 꺼냈을 뿐입니다. 검색이 아니라 조회라 실패하지 않습니다.

ScienceON은 다중 저자를 `김건우;윤영빈;` / `(주)유스풀제스트;(주)유스풀제스트;`처럼
**순서를 맞춰** 주므로 학술지 논문에도 그대로 쓸 수 있었습니다. KCI 제목 검색은 22편 중
7편만 맞았습니다(괄호·특수문자로 실패, 일부는 KCI에 아예 없음).

### 결과

| | 전 | 후 |
|---|---|---|
| 코퍼스 커버리지 | 823 / 1,000 (82.3%) | **1,000 / 1,000 (100%)** |
| DIKO | 0 / 150 | 150 / 150 |
| CFKO | 0 / 3 | 3 / 3 |
| **검색 불가 저자** | 203명 | **0명** |

### 다만 이들의 프로필은 빈약하다

| | 학위논문 출신 153명 | 일반(KCI) 1,698명 |
|---|---|---|
| 평균 논문 수 | **1.00편** | 19.2편 |
| 피인용 보유 | 1명 | 전원 |
| 이메일 | 0명 | 494명 |
| 공저자 | 0명 (단독 저자) | 평균 33.9명 |

**"검색에서 사라지는 것보다 낫다" 수준이지 온전한 프로필이 아닙니다.**
명세서의 "데이터 없음" 폴백이 이 153명(전체의 5%)에서 자주 발동합니다.

### 함께 고친 것

- **기관명 파싱 버그** — 최장일치 규칙이 하위조직 접미사를 삼켰습니다.
  `한서대학교 문화재보존과학연구센터`에서 뒤의 '센터'가 '대학교'를 이겨 통째로 루트가 됐고,
  그 값이 KCI `affiliation` 필터에 들어가 논문이 안 잡혔습니다(이유진 1,426건 → 1건).
  정확한 규칙은 **가장 이른 시작 위치에서 가장 긴 접미사**입니다 — 최초종료로 고치면
  `연세대학교`가 `연세대학`으로 잘립니다. 두 실패를 `tests/test_institution_root.py`에
  25개 케이스로 고정했습니다. 허경행 3→15편, 송영조 1→6편 회복.
- **전공 필드 오염 256건** — `한양대학교 대학원`의 '대학원'을 전공에 넣고 있었습니다.
  `Yonsei University`는 루트 `Yonsei` + 전공 `University`로 잘렸습니다.
- **세미콜론 미분리 행 2건** — 다중 저자 처리를 넣기 전 첫 실행이 `윤종민;한갑운;김현수;`를
  한 사람 이름으로 만들어 남겨뒀습니다(upsert라 재실행해도 안 지워짐).
- **임베딩 누락 11명** — 학술대회 논문 저자는 키워드가 없어 벡터가 안 만들어졌습니다.

## 12. 서지 지표 수집 (2026-08-23)

명세서 「연도별 논문 이력」의 각 항목에 **논문 유형**이 있는데 외부 논문에는 컬럼이 없었습니다.
확인해보니 `paper_type`은 API 필드가 아니라 출처에서 파생하는 값이었고(`papers`도 `DBCode`로 분류),
KCI articleSearch로 모은 논문은 정의상 등재지 학술논문이라 **`UPDATE` 한 번으로 33,179편이 확정**됐습니다.

### 안 뽑고 있던 필드를 발견했다

`articleDetail` 응답 전체를 훑어보니 쓰고 있지 않던 값이 넷 있었습니다. `keywords` 단계가
이미 이 API를 25,285편에 호출하고 있었으므로 **그때 같이 뽑았으면 공짜였습니다.**

| 필드 | 채움 | 쓸모 |
|---|---|---|
| **`fwci`** | 32,882 (99.1%) | **분야보정 피인용** — 분야 평균을 1.0으로 맞춘 값 |
| `kci-registration` | 33,167 | 등재 29,146 / 우수등재 629 / 등재후보 2,851 / 미등재 486 |
| `article-language` | 30,086 | 한국어 23,383 / 영어 6,691 |
| `article-regularity` | 33,179 | 정규 논문 여부 |

### fwci가 왜 중요한가

§5에서 확정한 "피인용은 출처를 섞지 않는다"의 근본 원인은 **집계 범위가 달라 비교가 안 된다**는 것이었습니다.

```
피인용 원값 : KCI 중앙값 20  vs  OpenAlex 중앙값 709   ← 35배, 한 척도 불가
fwci        : 중앙값 1.07, 최대 60.88                  ← 분야 평균 1.0 기준
```

fwci는 같은 분야·같은 연차 논문의 평균 인용을 1.0으로 놓고 보정한 값이라, 농학과 의학을,
2005년과 2024년을 같은 자로 잽니다. 노드 크기를 하나의 척도로 통일할 여지가 생깁니다.
다만 **OpenAlex 쪽에는 fwci가 없어 완전 통일은 아직 안 됩니다.**

당초 "옛날 논문에는 fwci가 없을 것"이라 예상했는데 **연차와 무관하게 99% 이상**이었습니다
(2000년대 100%). 시범 12편에서 5편만 나온 건 표본이 작았던 탓입니다.

### 도중에 잡은 버그

체크포인트에 키워드만 담긴 옛 형식이 남아 있었습니다. 그대로 뒀으면 "이미 처리함"으로 판단해
**26,448편 재수집이 통째로 건너뛰어지고 fwci가 하나도 안 들어왔을 것**입니다.
형식이 다르면 무효로 보도록 고쳤습니다.

## 13. 동명이인 LLM 판정 (2026-08-23)

규칙으로 못 가르는 쌍이 13개 남았습니다 — 같은 이름인데 한쪽 소속은 한글, 한쪽은 로마자이고
공저자가 하나도 안 겹치는 경우입니다. **기관명 대조표가 있어야 푸는 문제**라 규칙으로는 한계가
있고, 임베딩으로도 안 됩니다(§2의 실측: 같은 곳 0.398 < 다른 곳 0.434로 겹침).

전수가 아니라 **규칙이 포기한 13쌍만** LLM에 넘깁니다. 기존 `app/services/llm/client.py`의
예산 한도·캐시·비용 누적을 그대로 씁니다.

| 판정 | 건수 | 예 |
|---|---|---|
| **합침** | **1** | 김봉규 — 경남과학기술대학교가 2021년 통합돼 **Gyeongsang National University** |
| 분리 유지 | 10 | 김지현 4쌍 — 고려대·이화여대·한양대·진주보건대 vs 부산대 |
| 보류 | 2 | 조혜준(같은 기관이나 시기 공백), 장일한(유학 가능성) |

**김봉규가 정확히 규칙의 사각지대입니다.** 기관 통합·개명 이력은 문자열로도 임베딩으로도
알 수 없습니다. 병합 후 논문 31 → 32편, 소속 이력에 국·영문 표기가 모두 남습니다.

### 안전장치

- **확신도 0.8 미만은 합치지 않습니다.** LLM이 `same`이라 해도 확신이 낮으면 넘어갑니다.
- **프롬프트에 비대칭 비용을 명시**했습니다 — "확신이 없으면 unknown. 틀리게 합치는 쪽이
  나누어 두는 쪽보다 나쁘다." 실제로 조혜준·장일한을 스스로 유보했습니다.
- **응답 잘림을 조용히 삼키지 않습니다.** 첫 실행에서 `max_tokens=300`에 걸려 김봉규 판정
  (`same 0.9`)이 JSON 미완성으로 `unknown`이 됐습니다. **판정이 있었는데 없는 것처럼 처리되는 게
  가장 나쁜 실패**라, 파싱 실패는 따로 세고 체크포인트에 남기지 않아 다음 실행에서 재시도됩니다.

## 14. 서비스 계층 정리 (2026-08-23)

`app/services/researcher_similarity.py`에 프런트가 정할 것이 들어가 있었습니다 —
`NODE_RADIUS_MIN = 8.0px`, `NODE_RADIUS_MAX = 28.0px`, 엣지 임계값, 노드/엣지 생성.
**백엔드는 점수까지만 주고, 몇 px로 그릴지는 프런트가 정합니다.**

계산 자체도 틀렸습니다. 로우와프 3쪽을 확인하니 **중심에 검색 키워드가 있고 연구자가 그 주위를
둘러싸는 별 모양**이고, 명세서 문구도 "**키워드에** 가까울수록"입니다. 저는 이걸 "연구자끼리
가까울수록"으로 읽고 쌍별 유사도를 계산하고 있었습니다.

```
전:  연구자 14명 → 쌍별 유사도 91개 → 임계값 넘는 엣지 45개   ← 와이어프레임에 없는 형태
후:  키워드 1개 + 연구자 N명 → 각자 키워드와의 거리 1개씩      ← 별 모양에 맞음
```

| 백엔드가 주는 것 | 프런트가 정하는 것 |
|---|---|
| `affinity` 0~1 (키워드와의 거리) | 중심에서 몇 px 떨어뜨릴지 |
| `citations` + **`citation_source`** | 원을 몇 px로 그릴지 |
| 이름·소속·전공·논문수 | 배치·색·선 |

`citation_source`를 함께 내려줍니다 — KCI와 OpenAlex 피인용은 중앙값이 35배 차이나서
**한 척도로 크기를 매기면 안 된다**는 걸 프런트가 알아야 하기 때문입니다.

`similar_researchers()`(내용 70% + 그래프 30%)와 `pairwise_similarity()`는 남겼습니다.
